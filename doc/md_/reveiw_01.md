### Общий обзор

Библиотека `marty_cbp` представляет собой концепт-реализацию клиента для Chrome DevTools Protocol (CDP). Она предоставляет базовые возможности: HTTP-запросы к /json/list, /json/version, /json/new, запуск Chrome с нужными аргументами, WebSocket-соединение, отправку команд и подписку на события. Код написан в стиле «прототип» – многие непонятные ситуации вызывают исключения, что допустимо на данном этапе.

Тем не менее, в текущей реализации выявлен ряд серьёзных проблем, которые могут привести к **дедлокам, утечкам процессов, некорректной обработке сообщений и ошибкам компиляции**. Ниже приведён детальный список недостатков с пояснениями и рекомендациями.

---

### 1. Потенциальные дедлоки при вызове обработчиков

**Проблема:**  
В методах `processMessage()` и `findIdHandler()` обработчик (`MessageHandlerType` или `SystemEventHandlerType`) вызывается внутри критической секции, удерживающей мьютекс соответствующей структуры данных.  
- `findIdHandler()` удерживает `m_idQueueMutex` во время вызова обработчика.  
- `findSystemEventHandler()` удерживает `m_systemHandlersMutex`.  
- `findMethodEventHandler()` удерживает `m_methodHandlersMutex` (и кеш-мьютекс).

Если обработчик (предоставленный пользователем) попытается вызвать любой метод `Connection`, который снова захватывает тот же мьютекс (например, `wsSendCommand()` → `enqueIdHandler()`), возникнет **дедлок**, так как мьютексы нерекурсивны (`std::mutex`).

**Пример:**
```cpp
wsConnection->wsSetDefaultIdHandler([&](auto...) {
    wsConnection->wsSendCommand("Page.navigate", {}); // попытка захватить m_idQueueMutex повторно
});
```
После получения ответа по id, `findIdHandler()` вызовет этот лямбда-обработчик, удерживая мьютекс, и произойдёт deadlock.

**Решение:**  
Перед вызовом обработчика необходимо освободить мьютекс. Например, извлечь обработчик из контейнера, разблокировать, а затем вызвать.

### 2. Неверная обработка бинарных WebSocket-сообщений

**Проблема:**  
В `processMessage()` для сообщений типа `Message` проверяется флаг `binary`. Если `msg.binary == true`, JSON не парсится, но код всё равно пытается обратиться к `j.contains("id")`. Поскольку `j` остаётся пустым (null), все проверки провалятся, и будет выброшено исключение `"unknown Message type"`.  
CDP использует текстовые JSON-сообщения, но в будущем могут появиться бинарные (например, для передачи скриншотов). Текущая реализация не обрабатывает их корректно.

**Решение:**  
Либо игнорировать бинарные сообщения, либо добавить поддержку (например, передавать их в специальный обработчик). Как минимум, не бросать исключение.

---

### 3. Некорректная отправка параметров команд (null вместо пустого объекта)

**Проблема:**  
В `wsSendCommand()` параметры формируются так:
```cpp
json j = { {"id", cmdId}, {"method", method} };
j["params"] = params; // если params == json(), то поле будет "params": null
```
Согласно спецификации CDP, ключ `params` **должен быть объектом** или отсутствовать. Отправка `null` может привести к ошибке на стороне браузера.

**Решение:**  
Добавлять `params` только если он не null, или всегда передавать пустой объект `json::object()`.

---

### 4. Ошибка компиляции в тестовом обработчике (static_assert)

**Проблема:**  
В `_test16.cpp` в `std::visit` используется ветка `else` с `static_assert(false, ...)`. В C++17 такой `static_assert` срабатывает всегда, даже внутри неинстанцированной ветви `constexpr if`, что приводит к ошибке компиляции.  
На практике это может не проявляться, если компилятор поддерживает более новый стандарт (C++23) или имеет расширение, но по стандарту это некорректно.

**Решение:**  
Использовать шаблонный вспомогательный тип для `always_false`:
```cpp
template <class> struct always_false : std::false_type {};
...
else static_assert(always_false<T>::value, "non-exhaustive visitor!");
```

### 5. Утечка процессов Chrome при неудачном подключении

**Проблема:**  
В `runConnectAndGetJsonList()` после успешного `spawnProcess()` выполняется цикл попыток подключения. Если все попытки неудачны, функция возвращает ошибку, но **запущенный процесс Chrome остаётся висеть** (его PID не сохраняется и не убивается). Это приводит к накоплению «зомби-процессов».

**Решение:**  
Сохранять PID и завершать процесс при неудаче, либо использовать механизм автоматического закрытия при разрушении объекта.

---

### 6. Отсутствие проверки коллизий портов

**Проблема:**  
`generatePortNumberForProjectConnection()` вычисляет порт на основе хеша пути проекта, но не проверяет, не занят ли этот порт другим экземпляром Chrome. В комментарии упоминается проверка через `/json/version`, но она не реализована. Это может привести к конфликтам, если два проекта используют один порт.

**Решение:**  
Реализовать проверку доступности порта (попытка подключения к `/json/version`) и, в случае коллизии, сгенерировать другой порт (например, инкрементировать до свободного).

---

### 7. Слишком низкие таймауты по умолчанию

**Проблема:**  
В `types.h` для `Timeouts` установлены значения `connectTimeout = 1` и `transferTimeout = 1` (секунда). Для запуска Chrome и первых HTTP-запросов этого может быть недостаточно, особенно на медленных машинах или при высокой нагрузке. В тесте используется `{1,3}` для подключения, но по умолчанию могут возникать ложные ошибки.

**Решение:**  
Увеличить значения по умолчанию, например, до 5–10 секунд, или дать пользователю явно их задавать.

---

### 8. Небезопасное использование mutex при вызове обработчиков (также проблема 1)

Уже описано выше – дополнительно отметим, что аналогичная проблема есть и для системных обработчиков (`findSystemEventHandler`).

---

### 9. Отсутствие поддержки удаления обработчиков

**Проблема:**  
Методы `wsSetMethodEventHandler()` и аналогичные перезаписывают обработчики, но не позволяют удалить уже установленный (кроме как перезаписью пустым). Это не критично для концепта, но может усложнить использование.

---

### 10. Неэффективный поиск обработчиков по id

**Проблема:**  
`findIdHandler()` выполняет линейный поиск по `m_idQueue` (deque). При большом количестве параллельных запросов (сотни) это может стать узким местом. Хотя для прототипа допустимо, в перспективе стоит использовать `std::unordered_map<unsigned, handler>`.

---

### 11. Неполная обработка HTTP-ошибок

**Проблема:**  
В `runConnectAndGetJsonList()` проверяется только `ixHttpErrorCodeIsOk()` и `ixHttpErrorCodeCantConnect()`. Другие ошибки (например, `CannotCreateSocket`, `SendError`) считаются фатальными и приводят к немедленному возврату, хотя, возможно, стоит повторить попытку или перезапустить Chrome.

---

### 12. Неинтуитивное поведение `wsStart()` и `wsStop()` с атомарным счётчиком

**Проблема:**  
Счётчик `m_wsStartCounter` позволяет стартовать/останавливать только один раз. Это корректно, но если пользователь вызовет `wsStop()` дважды, второй вызов ничего не сделает (так как ожидает `expected=1`). Это может скрыть логические ошибки в клиентском коде.

---

### 13. Отсутствие метода для получения состояния WebSocket

**Проблема:**  
Нет способа узнать, установлено ли соединение (`getReadyState()`). Пользователь вынужден полагаться на системные обработчики или флаги.

---

### 14. Потенциальная гонка при вызове `wsDispatchMessages()` из нескольких потоков

**Проблема:**  
Хотя `getQueuedMessage()` защищена мьютексом, `processMessage()` может вызывать обработчики, которые не являются потокобезопасными. Библиотека не гарантирует, что обработчики будут вызваны только из одного потока. Если пользователь вызовет `wsDispatchMessages()` из двух потоков одновременно, обработчики могут выполняться параллельно, что может привести к состояниям гонки в пользовательском коде.

**Решение:**  
Документировать, что `wsDispatchMessages()` не предназначен для параллельного вызова, или добавить внутренний мьютекс для сериализации обработки.

---

### 15. Отсутствие проверки на `nullptr` при вызове обработчиков

**Проблема:**  
В коде есть проверка `if (idHandler)`, но `std::function` неявно преобразуется в bool, так что это корректно. Однако при вызове через `operator()` не проверяется, что обработчик не пуст. Это уже учтено, но если обработчик пустой, он просто игнорируется (что правильно).

---

### 16. Ошибка в генерации шаблонов для `generatePatterns()`

**Проблема:**  
Функция `generatePatterns()` возвращает шаблоны для метода, но не учитывает, что в CDP имена могут содержать не только точки, но и другие разделители. Сейчас используется только '.', что соответствует спецификации, но недокументировано. Это не ошибка, но стоит отметить.

---

### 17. Использование `mutable` для `m_idQueue` и других полей

**Проблема:**  
Это позволяет изменять очередь в константных методах (например, `findIdHandler()` объявлена `const`). Это допустимо, но может ввести в заблуждение. Лучше было бы сделать такие методы неконстантными или явно документировать.

---

### 18. Отсутствие обработки исключений при парсинге JSON

**Проблема:**  
В `httpGetJsonList()` и других методах вызов `from_json(j, list)` может выбросить исключение, если JSON не соответствует структуре. Исключение пробрасывается выше, что для концепта допустимо, но в конечной реализации стоит перехватывать и логировать ошибки.

---

### 19. Неправильная обработка параметров в `checkRunAndGetJsonList()`

**Проблема:**  
Перегрузка `checkRunAndGetJsonList(list, chromeName, spawnArgs)` вызывает основную версию с `probeTimeouts = m_httpTimeouts`. Это означает, что для первоначальной проверки и для повторных попыток используются одни и те же таймауты, хотя логичнее было бы использовать разные (например, для первоначальной проверки – короткий таймаут, для повторных – длиннее). В тесте это исправлено явной передачей `httpProbeTimeouts`.

---

### 20. Отсутствие метода для явного завершения WebSocket-соединения (graceful shutdown)

**Проблема:**  
`wsStop()` вызывает `m_webSocket.stop()`, который закрывает соединение, но не даёт возможности отправить управляющий кадр Close. Для CDP это не критично, но может быть полезно.

---

### 21. Неполное тестирование – не проверяются сценарии с ошибками

**Проблема:**  
Тест `_test16.cpp` проверяет только успешный сценарий. Нет тестов на:
- недоступность порта;
- отсутствие Chrome;
- ошибки WebSocket;
- некорректные команды.

---

### 22. Зависимость от внешних библиотек (umba, ixwebsocket, nlohmann/json)

**Проблема:**  
Это не ошибка, но для production стоит явно указывать версии и обеспечивать удобную интеграцию (через CMake, vcpkg и т.п.).

---

### Резюме

Наиболее критичные проблемы:
1. **Дедлоки при вызове обработчиков** – необходимо освобождать мьютексы перед вызовом.
2. **Некорректная отправка `params: null`** – исправить на пустой объект или отсутствие поля.
3. **Утечка процессов** – добавить управление временем жизни процесса.
4. **Ошибка компиляции в тесте** – исправить `static_assert`.

Остальные замечания касаются удобства, производительности и надёжности. Рекомендуется доработать библиотеку с учётом этих пунктов перед использованием в production.

### Обновлённый перечень проблем

1. **Некорректная обработка бинарных WebSocket-сообщений**  
   В `processMessage()` для `Message`‑сообщений с флагом `binary == true` JSON не парсится, но код всё равно обращается к `j.contains(...)`, что приводит к исключению. Необходимо либо обрабатывать бинарные данные отдельно, либо документировать, что они не поддерживаются.

2. **Отправка `params: null` вместо пустого объекта**  
   В `wsSendCommand()` при пустых `params` в JSON добавляется поле `{"params": null}`, что не соответствует спецификации CDP (параметр должен быть объектом или отсутствовать). Рекомендуется добавлять поле только если `!params.is_null()`.

3. **Утечка процессов Chrome при неудачном подключении**  
   В `runConnectAndGetJsonList()` после успешного запуска процесса, если все попытки подключения провалились, процесс не завершается. Нужно сохранять PID и убивать процесс при ошибке.

4. **Отсутствие проверки коллизий портов**  
   Порт вычисляется хешем пути, но не проверяется, не занят ли он другим экземпляром Chrome. В комментарии упоминается проверка через `/json/version`, но она не реализована.

5. **Слишком низкие таймауты по умолчанию**  
   `Timeouts` имеют значения 1 секунда, что может быть недостаточно для запуска браузера. Рекомендуется увеличить значения или сделать их настраиваемыми.

6. **Ошибка компиляции в тестовом обработчике (`static_assert`)**  
   В `_test16.cpp` внутри `std::visit` используется `static_assert(false, ...)` в ветке `else` внутри `constexpr if` – это некорректно по стандарту. Нужно использовать шаблонный `always_false`.

7. **Неэффективный поиск обработчиков по `id`**  
   `findIdHandler()` использует линейный поиск по `std::deque`. При большом количестве запросов это может стать узким местом. Лучше использовать `unordered_map`.

8. **Неполная обработка HTTP-ошибок**  
   В `runConnectAndGetJsonList()` обрабатываются только `Ok` и `CannotConnect`/`Timeout`; другие ошибки (`SendError`, `CannotCreateSocket` и т.п.) считаются фатальными, хотя возможно стоит повторить попытку.

9. **Неинтуитивное поведение `wsStart()`/`wsStop()` с атомарным счётчиком**  
   Счётчик позволяет запустить/остановить только один раз. Повторные вызовы игнорируются, что может скрывать логические ошибки.

10. **Отсутствие метода для получения состояния WebSocket**  
    Нет способа узнать, установлено ли соединение (например, `getReadyState()`).

11. **Потенциальная гонка при вызове `wsDispatchMessages()` из нескольких потоков**  
    Хотя очередь защищена, обработчики могут вызываться параллельно, если пользователь запустит `wsDispatchMessages()` в нескольких потоках. Необходимо документировать, что метод не является потокобезопасным.

12. **Отсутствие поддержки удаления обработчиков**  
    Нет метода для удаления ранее установленных обработчиков (кроме перезаписи).

13. **Ошибка в генерации шаблонов `generatePatterns()`**  
    Функция предполагает только разделитель `'.'`, что соответствует CDP, но стоит явно документировать.

14. **Использование `mutable` для контейнеров с обработчиками**  
    Поля `m_idQueue`, `m_systemHandlers` и др. объявлены `mutable` для использования в `const`‑методах. Это допустимо, но может ввести в заблуждение.

15. **Отсутствие обработки исключений при парсинге JSON**  
    Вызовы `from_json()` могут бросать исключения, которые пробрасываются дальше. Для прототипа допустимо, но в релизной версии стоит перехватывать и логировать.

16. **Неправильная передача таймаутов в `checkRunAndGetJsonList()`**  
    Перегрузка без явного `probeTimeouts` использует `m_httpTimeouts` для обеих фаз (проверки и подключения), хотя логичнее использовать разные значения.

17. **Отсутствие graceful shutdown WebSocket**  
    `wsStop()` не даёт возможности отправить управляющий кадр Close.

18. **Неполное тестирование**  
    В примере отсутствуют сценарии с ошибками (недоступность порта, отсутствие Chrome и т.п.).

19. **Зависимость от внешних библиотек без спецификации версий**  
    Для production следует явно указать версии `ixwebsocket`, `nlohmann/json` и `umba`.
